# 客服压测台 · 阶段验证

本项目已完成阶段 0–2 的验证工具与三轮实验，完整产品尚未完成。实验未通过预先设定的继续开发门槛，因此停止扩大开发。

## 场景与证据边界

这里是**真实模型调用 + 虚构业务场景**。店铺规则、商品、顾客剧本与订单均为实验样例，不是真实商家业务。原始 JSON 保留的“虚构演示数据”字段指业务输入；表中数字来自已保存的真实运行结果。

## 已完成的工作

模型接口、三角色上下文隔离、多轮编排、结构化裁判、逐字引用校验、超时重试、持久预算、断点续跑、运行留痕和 Markdown 报告。阶段交付记录为 47 项工程测试通过；这不代表模型判断准确率通过。

每轮包括预埋缺陷、严格客服、政策泄露三个对照组，各 24 场。C5 要求五类缺陷中至少四类在目标剧本的三次重复中至少两次以正确类型检出；最终 0/5 表示无缺陷类别达标，不表示所有对话都没有检出问题。C6 要求严格客服在 S13/S14 六场对话中，被判中高问题的比例不超过 20%。严格客服也可能真的答错，**C6 不是人工确认的误报率**。

最终轮完成 72/72 场、判定可解析 72/72 份、逐字引用有效 34/35（含重试前无效引用）。引用有效只说明原话存在，不能证明判定类型、理由和严重度正确。人工准确率和一致率仍待标注。

三轮累计 216 场阶段 2 对话；全项目累计 1,527 次真实调用、1,782,141 个已知 token，预算扣记 1,797,571 个 token，其中 1 次调用用量未知并保留保守预留。已知用量不是精确账单；未推算费用或业务收益。见[跨轮汇总](g2-history.json)。

## 复盘与取舍

1. 缺陷指令确实进入请求，不代表被测客服稳定输出目标错误。
2. 模拟顾客可能改写订单事实，导致形式命中被污染。
3. 严格客服也会犯错，不能把它当作裁判的标准答案。

两次修复只调整顾客与裁判提示词，规则、商品、缺陷、剧本、客服及通过阈值保持不变。三轮均未通过，结果全部保留，停止阶段 3–6。下一步建议先建立人工确认的对话基准，独立验证裁判，再检查模拟追问的增益与真实使用价值。该计划尚未执行。
